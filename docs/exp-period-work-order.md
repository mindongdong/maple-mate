## 0. 요약

- **문제(유저 피드백):** 서버 리더보드(무인자 Top10)의 7일 그래프에서 고레벨 유저의 상승이 안 보인다. Y축이 표시된 선 전체의 레벨 범위(예: Lv.260~290)에 맞춰지기 때문에, 고레벨이 7일 동안 올린 +0.3레벨은 평평하게 그려진다.
- **해결 두 가지:** ① 기본 기간을 **30일**로 늘리고 명령어에서 7/14/30일을 고를 수 있게 한다. ② 선 끝 라벨과 임베드 순위판에 **기간 증가량(`+132%`)** 을 붙인다. 기간을 늘려도 격차 큰 서버에선 여전히 평평할 수 있어서, 증가량 숫자가 주된 보완이다.
- **최적화:** 긴 기간은 **달력 고정 샘플 날짜**만 조회하고 표시한다(30일 = 3일 간격). 기간 백필은 **실제로 표시되는 Top10(지정 시 그 유저들)만** 대상으로 한다.
- **스키마 변경 없음.** 스냅샷 보관 90일(`RETENTION_DAYS`)이라 30일은 기존 데이터 안에 들어온다.

## 1. 확정 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 피드백 출처는 **서버 리더보드**다. 기간 확장만으로는 부족하므로 **증가량 표기를 같이 넣는다** | 레벨 격차가 Y축 범위를 지배한다 |
| D2 | 증가량 단위는 **레벨 내 % 누적**: `(끝 progress − 시작 progress) × 100`, 정수 반올림, 부호 표기(`+132%`, 사망 페널티로 줄었으면 `-3%`) | 메이플 유저의 "몇 % 먹었다" 감각에 맞다. 누적 경험치는 ADR-0020에서 total_exp를 폐기해서 쓸 수 없다. 레벨대별 필요 경험치 차이는 감수한다 |
| D3 | 시작점은 **기간 안의 첫 유효 샘플점**, 끝점은 **오늘 라이브 점**(라이브 실패 시 마지막 유효점). 유효점이 1개 이하면 증가량을 생략한다 | 시작점이 비는 건 대개 새 캐릭터라 그 기간 실제 증가량이 맞다. 일시 장애로 비어도 다음 샘플점에서 시작하니 오차가 작다 |
| D4 | 증가량은 **모든 기간(7일 포함)** 에, **그래프 선 끝 라벨 + 임베드 순위판** 양쪽에 표시한다. 푸터에 `증가량: 최근 N일`을 명시한다. `/내캐릭터 경험치`는 같은 코어라 자동 적용된다 | 피드백 화면(10시 알림)에 바로 효과를 낸다 |
| D5 | **기본 30일**, 명령어 `기간` 옵션 `30일 / 14일 / 7일`. **10시 자동 알림은 30일 고정**(알림별 기간 설정 없음 → 스키마 변경 없음). 대상 지정 비교(유저1~5)에도 적용한다 | 알림 기간 수요는 근거가 없다. 필요해지면 `/경험치알림 켜기 기간:`을 나중에 추가할 수 있다(충돌 없음) |
| D6 | 간격: 30일=3일, 14일=2일, 7일=1일. **달력 앵커**(`d.toordinal() % step == 0`) + 기준일(ref_date) + 오늘 라이브 점. **표시도 샘플 점만** 한다. X축은 **실제 날짜 비례** | 기준일부터 거꾸로 잡으면 날짜 세트가 매일 밀려 재사용이 안 된다. 달력에 고정하면 캐릭터당 하루 최대 1콜이다. 점 30개 × 10명은 과밀하다 |
| D7 | 백필을 2단계로 나눈다: ① 순위용 = 전체 캐릭터 × 최근 8일(기존 그대로) ② 그래프용 = 순위 확정 후 **표시 대상만** × 기간 내 샘플 날짜 중 빈 날. ②는 `build_targets_payload` 안(순위 직후, 렌더 전)에서 한다 | 콜드 비용 약 110콜(약 28초), 정상 상태는 하루 캐릭터당 최대 1콜. 알림 서버 수가 적어 배포 당일 1회 몰리는 콜은 감수한다(사전 워밍 스크립트 없음) |
| D8 | `/경험치`의 `기간` 옵션은 **유저1~5보다 앞**에 둔다. `/내캐릭터 경험치`에도 같은 옵션을 넣는다. 명령 설명문은 "최근 30일 레벨 추이와 증가량 (기간 변경 가능)"로 바꾼다. 사이트 문구와 샷은 **사이트 PR 2**에서 교체한다 | 옵션이 뒤에 있으면 목록 끝에 묻힌다 |
| D9 | **ADR-0011에 개정 섹션을 추가**한다(새 ADR 아님) | 표시 결정의 연장이다. Top10 통일 개정과 같은 관례 |

### D9 개정에 담을 근거
- 증가량은 **순위에 쓰지 않는 보조 숫자**다. 그래프 높이와 순위는 여전히 총 레벨이므로, D-7 정규화를 기각한 사유("시각 순위 ≠ 레벨 순위")와 충돌하지 않는다.
- 증가량은 레벨 내 % 기준이고 누적 경험치가 아니다(ADR-0020 제약).
- 알림에 기간 옵션이 없는 이유와 달력 앵커를 쓰는 이유(콜 재사용).

## 2. PR 1 — 봇

### 0단계: 시각화 게이트 (구현 착수 전)
- 실제 DB(또는 로컬 덤프) 데이터로 **30일 / 3일 간격 그래프를 스파이크 렌더**해서 눈으로 확인한다: 고레벨 선의 기울기, 10명 라벨 겹침(라벨이 `+132%`만큼 길어짐), X축 날짜 라벨 밀도.
- 30일인데도 평평하다면 증가량 숫자가 보완해 주는지 확인하고, 그래도 부족하면 **기본값을 다시 논의**한다(D5 전제).

### 작업 목록

**`maple_mate/leaderboard/service.py`**
- `HISTORY_DAYS = 7`을 기간 상수로 교체한다: `PERIOD_STEPS = {30: 3, 14: 2, 7: 1}`, `DEFAULT_PERIOD_DAYS = 30`.
- 순수 함수 `sample_dates(ref_date, days) -> list[date]`: 창 `ref_date-(days-1)..ref_date` 안에서 `toordinal() % step == 0`인 날 + ref_date(중복 제거, 오름차순).
- `history_progress(..., dates: Sequence[date])`: 연속 일자 대신 주어진 샘플 날짜만 조회한다(`snapshot_date.in_(dates)`).
- `backfill(..., dates: Sequence[date] | None = None)`: 날짜 목록을 받을 수 있게 한다(None = 기존 최근 `BACKFILL_DAYS`일). 멱등 로직은 그대로 둔다. **as-built:** `dates` 지정 시 최신 → 과거로 조회하다 첫 실패에서 그 캐릭터를 멈춘다(코드리뷰 MEDIUM — 생성 전·데이터 없는 날짜의 매 호출 재조회 방지, 실측 4콜 → 1콜).
- 순수 함수 `gains(series) -> dict[label, int | None]`: D2/D3 규칙. 라이브 점을 붙인 뒤의 series를 입력으로 받는다.

**`maple_mate/leaderboard/broadcast.py`**
- `build_targets_payload(..., period_days: int = DEFAULT_PERIOD_DAYS)`: 순위 → Top10 확정 → **표시 대상만 `backfill(dates=sample_dates)`**(D7 ②) → `history_progress(dates)` → 라이브 점 → `gains` → 렌더.
- `_rank_line`에 증가량을 붙인다: `🥇 **동민** — Lv.287 (79%) · +132%`(None이면 생략).
- `_footer_text`에 `증가량: 최근 N일`을 추가한다.
- `build_payload` / `build_specified_payload`에 `period_days`를 관통시킨다. `run_leaderboard_job`은 기본값(30)을 쓴다.

**`maple_mate/bot/leaderboard_image.py`**
- `render_progress_graph(series, ref_date, gains)`: X 좌표를 **날짜 비례**(`(d - dates[0]).days`)로 바꾸고, 날짜 라벨은 샘플 날짜에 둔다(30일 약 12개, 과밀하면 솎기). 끝 라벨은 `닉 Lv.287 (79%) +132%`. 라벨이 길어지므로 `subplots_adjust(right=…)`는 0단계 결과에 맞춰 조정한다.

**`maple_mate/leaderboard/commands.py`**
- `/경험치`: `기간` 선택 옵션(30/14/7, 기본 30)을 **첫 번째 파라미터**로 추가한다. 설명문을 갱신한다(D8).

**`maple_mate/mychar/commands.py`**
- `/내캐릭터 경험치`: 같은 `기간` 옵션을 넣는다. `handle_my_exp` → `build_targets_payload(period_days=…)`.

**문서**
- ADR-0011 개정 섹션(D9).

### 테스트 (TDD)
- `sample_dates`: 기간별 간격, ref_date 포함, **ref_date를 하루씩 옮겨도 앵커 날짜가 유지되는지**(재사용 보장).
- `gains`: 정상 / 레벨업을 넘는 경우(287.79 − 286.47 → `+132`) / 시작점 결손 시 첫 유효점 / 유효점 1개 → None / 라이브 실패 시 마지막 유효점 / 감소(음수).
- 기간 백필: **표시 대상 × 빈 샘플 날짜만** 넥슨을 호출하는지 콜 수로 단언. 비표시 캐릭터는 0콜.
- `history_progress(dates)`: 샘플 날짜만 반환하는지.
- 렌더러: 불균등 간격 입력에서 예외가 없는지 + PNG를 눈으로 확인(30·14·7일 각 1장).
- 기존 7일 경로 회귀: `기간:7일`의 결과가 이전 그래프와 동등한지(라벨 증가량 제외).

### 라이브 검증
- 실제 넥슨 데이터로 30일 콜드 백필(새 서버/캐릭터 가정)의 콜 수와 소요 시간 측정(예상: 10명 약 110콜, 약 28초).
- 디스코드에서 `/경험치`(기본), `/경험치 기간:7일`, `/경험치 유저1:@…`, `/내캐릭터 경험치 기간:14일` 각 1회 눈확인.

## 4. 스코프 아웃
- 알림별 기간 설정(`/경험치알림 켜기 기간:`): 수요가 생기면 추가한다.
- 60·90일 기간: 보관상 가능하지만 이번엔 열지 않는다.
- 누적 경험치 기반 증가량: ADR-0020으로 데이터가 없다.
- 그래프 정규화(성장 레이스): ADR-0011에서 기각됐고 재론하지 않는다.
