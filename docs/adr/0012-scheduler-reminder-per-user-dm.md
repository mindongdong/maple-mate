# ADR-0012 — 스케줄러 알리미: per-user DM 구독 모델 (채널 알림과 분기)

- **상태:** 채택 (Accepted)
- **일자:** 2026-06-26
- **관련 문서:** [CONTEXT.md](../../CONTEXT.md)(스케줄러 숙제·스케줄러 알리미), [docs/api/scheduler.md](../api/scheduler.md)(API 스펙·실호출 회귀), [docs/scheduler-feature-handoff.md](../scheduler-feature-handoff.md)(핸드오프), [ADR-0001](0001-nexon-personal-key-model.md)(개인 키 모델), [ADR-0009](0009-challengers-realm-model.md)(realm), [notification/scheduler.py](../../maple_mate/notification/scheduler.py)(cron 잡 등록)
- **이력:** `/grill-with-docs` 그릴링(2026-06-26) — 핸드오프 §3 열린 결정 9건 확정.

## 맥락 (Context)

신규 넥슨 `scheduler/character-state` API로 캐릭터의 인게임 "메이플 스케줄러" 숙제 현황(일일/주간 콘텐츠·퀘스트·보스)을 보여주는 기능을 만든다. 두 가지 표면을 원했다 — (1) 온디맨드 `/스케줄러` 조회, (2) **매일 정해진 시각(기본 오후 9시)에 자동으로 숙제 체크리스트를 받는 알림**.

기존 봇의 모든 자동 알림(썬데이·공지·경험치 리더보드)은 **채널 단위**다: `manage_guild` 권한자가 채널에 토글하고(`channel_settings`), **고정 시각** `CronTrigger` 잡이 채널로 브로드캐스트한다. 가장 쉬운 길은 이 패턴을 그대로 복제하는 것이었다.

그러나 스케줄러 숙제 데이터는 기존 채널 알림 소스와 성격이 다르다:

1. **개인 키 스코프 + per-character** (이력류 친척, ADR-0001) — 봇 앱 키로 임의 유저를 조회할 수 없다. 그 유저의 개인 키와 `ocid`가 있어야 한다.
2. **개인 관심사** — "내 숙제 다 했나"는 본인이 보는 것이다. 등록자 전원의 숙제를 채널에 공개하면 프라이버시 노출이고, 응답이 거대해(활성 캐릭 boss=77) 임베드를 넘긴다.
3. **시각 설정 요구** — "정해진 시각에 받고 싶다"는 본질적으로 per-user 선호다(서버 공통 시각은 부자연스럽다).

## 결정 (Decision)

**스케줄러 알리미는 기존 채널 알림 패턴을 따르지 않고, per-user DM 구독 모델로 만든다.**

1. **명령 분리:** `/스케줄러`(온디맨드 조회, ephemeral) + `/스케줄러알림 켜기·끄기`(구독 토글). Discord는 leaf와 group을 겸할 수 없어 `/스케줄러` + `/스케줄러 켜기` 공존이 불가 — `/경험치` + `/경험치알림` 선례를 따른다.
2. **구독 주체 = 본인.** `/스케줄러알림 켜기`는 **본인이 본인을 구독**한다(`manage_guild` 불요). 채널 토글(권한자가 채널을 켬)과 반대다. 발송은 **그 유저 DM**으로 간다.
3. **realm별 독립 구독.** 구독은 `(guild_id, discord_user_id, realm)` 단위 — 본서버·챌린저스를 따로 켜고 시각도 따로 둘 수 있다(ADR-0009). 본서버 구독은 본서버 캐릭터, 챌린저스 구독은 챌린저스 캐릭터를 본다.
   - **개정(2026-06-27): 대표 1캐릭 → 등록 캐릭터 전체.** 온디맨드·알림 모두 그 realm 대표 1명이 아니라 **그 realm에 등록한 캐릭터 전부**를 보여준다. 발송은 **캐릭터당 메시지 1개**(온디맨드 = ephemeral followup N개, 알림 = DM N개; 캐릭터 4개면 메시지 4개). 캐릭터별 임베드가 자기완결적이라 임베드 합치기 한계를 피하고, "내 모든 캐릭터 숙제를 한 번에"라는 본래 의도에 맞다. 캐릭터별 4xx(비대상·저활동)·빈 숙제는 조용히 스킵(결정 7 유지), 전부 비면 발송 0. 비용은 구독당 N콜이나 개인 키 스로틀·캐릭터 상한(10)으로 바운드. `resolve_self`(대표 ocid) → `resolve_self_characters`(키 + realm 캐릭터 전부), `build_homework` → `build_homeworks`(캐릭터별 Homework 리스트).
4. **시 단위 시각(기본 21시 KST), 행마다 저장.** 디스패치는 **매시 정각 cron 잡 1개**가 그 시각(`hour`) 구독 행을 조회해 발송한다. per-minute 디스패처를 피해 인프라를 단순화한다. cron 등록은 기존 `notification/scheduler.py:start_scheduler`에 둔다(잡 본체는 지연 import — leaderboard 패턴).
   - **개정(2026-06-28) → [ADR-0014](0014-scheduler-category-filter.md):** 구독 행이 `hour` 외에 **숙제 카테고리 필터 선호**(제외집합)도 갖게 됨. 알림은 발송 시점 상호작용이 없어 선호를 지속해야 하므로, `/스케줄러알림 켜기`가 4개 카테고리 on/off 파라미터를 받아 병합 저장한다(무상태 철학의 의도된 예외 — 사유는 ADR-0014).
5. **표시 = `registration_flag=="true"` 필터, 일일/주간/보스 3섹션 임베드.** 인게임 스케줄러에 직접 등록한 항목만 '내 숙제'로 본다. 콘텐츠 이름(`수로` 등)은 **특수 케이스로 하드코딩하지 않는다** — `content_name`은 자유 문자열이라 리네임 시 조용히 누락된다. 섹션별 일반 렌더로 자연 노출한다.
   - **as-built 개정(요약형, 2026-06-27):** 초기 안("완료·미완료 모두 한 줄씩 = 체크리스트")을 라이브로 찍어 보니 일일 점수형 콘텐츠(수로/조사)가 대부분 `0/100`이라 **균일한 텍스트 벽**이 되어 가독성이 무너졌다(스크린샷). 그래서 표시를 **요약형**으로 바꾼다: ① 섹션 헤더에 `완료/총 + 진행바`(보스는 `weekly_boss_clear_count/limit_count + 진행바`), ② 본문은 **진행 중만** `now/max` 게이지로 개별 표시(달성률 내림차순), ③ **미시작(now==0)은 이름만 한 줄로 접기**(`남은 N개 · a · b …`), ④ 완료는 수만(`완료 N개`), 보스는 **미처치(남은 보스)를 개별** + `처치 N개`. 콘텐츠명 앞 `[일일/웨스트]` 대괄호 프리픽스 제거 + 말줄임은 구조적 정리라 "하드코딩 금지"와 무관. 필터·3섹션·빌더 공유는 불변, **표시 규칙만** 바뀐다.
   - **개정 2(필드 파생 카테고리, 2026-06-27) → [ADR-0013](0013-scheduler-field-derived-categories.md):** 요약형(개정 1)도 "할 일 즉시 파악" 요구를 못 맞춰 폐기. 라이브 9캐릭 실 API 조사로 `type`/`quest_state`/`max_count`/`cycle` **필드 파생 카테고리**(퀘스트=완료/미완료·몬파=회수·길드=점수·보스=cycle별)로 재설계. **"3섹션 불변"은 폐기**(카테고리 세분화)하되 **"콘텐츠명 하드코딩 금지"는 필드 파생으로 보존**. 표시 규칙의 단일 출처는 이제 ADR-0013.
6. **온디맨드와 알림이 같은 빌더를 공유**한다(`/경험치`·`/경험치알림`이 `build_payload`를 공유하듯). 발송만 ephemeral 응답 vs 예약 DM으로 갈린다.
7. **발송 실패는 조용히 스킵 + 앱로그만.** 키 없음·대표 4xx·DM 차단·넥슨 일시 오류 모두 에러 DM·자동 해지 없이 넘긴다(운영 요약 철학 — "친구 개인 키 실패는 자가 발견"). 가드 2개: (a) `/스케줄러알림 켜기`는 키·대표 없으면 구독 시점에 거부(fail fast), (b) 등록 숙제 0개면 빈 DM 대신 스킵(전부 완료는 ✅ DM 발송).

## 검토한 대안 (Alternatives Considered)

- **채널 브로드캐스트(기존 패턴 복제)** — *기각.* 등록자 전원 숙제를 채널에 공개 → 프라이버시 노출, 개인 키 보유자만 표시, 응답 거대(보스 77)로 임베드 초과. per-user 시각 설정도 불가능. 구현은 가장 쉬우나 데이터 성격(개인 키·개인 관심사)과 충돌.
- **채널 넛지만('숙제 확인하세요' 알림 후 각자 /스케줄러)** — *기각.* "스케줄러 기능을 실행"(실제 체크리스트 산출) 요구를 충족하지 못한다.
- **시:분 단위 시각** — *기각.* per-minute 디스패처가 필요해 인프라·테스트가 복잡. 친구 서버 규모엔 시 단위로 충분.
- **콘텐츠 이름 특수 케이스(수로 핀 고정 등)** — *기각.* `content_name` 리네임/추가 시 조용히 깨진다. 일반 섹션 렌더가 견고.
- **실패 시 에러 DM / N회 실패 자동 해지** — *기각.* 매일 같은 에러 DM 스팸 위험, 실패 카운터 상태 추가로 복잡. 조용한 스킵 + 자가 발견이 봇의 기존 철학과 일치.

## 결과 (Consequences)

**긍정**
- 데이터 성격(개인 키·per-character·개인 관심사)에 맞는 전달 모델 → 프라이버시 보존, per-user 시각 설정 자연.
- 온디맨드·알림이 같은 빌더를 공유해 표시 일관.
- 매시 정각 cron 1개로 디스패치 → 기존 cron 인프라에 최소 추가.

**부담 / 잔류**
- **기존 채널 알림과 분기된 첫 사례** — `channel_settings` 토글이 아니라 신규 `scheduler_subscription` 테이블(PK `(guild_id, discord_user_id, realm)`, `hour`), DM 전달, per-user 스케줄링이 모두 새 경로다. "왜 이것만 채널이 아니라 DM·per-user인가"의 답이 이 ADR이다.
- **DM 차단 유저는 알릴 방법이 없다** — 조용히 스킵(애초에 DM이 막혀 통지 불가). 유저는 `/스케줄러` 수동 실행으로 자가 발견.
- **죽은 구독의 잉여 콜** — 미접속·키 철회 구독은 매일 1콜씩 헛돈다(개인 키 버킷 스로틀로 바운드, 등록자 수 수준이라 무해).
- **패키지 이름 `scheduler` 가 cron 파일 `notification/scheduler.py` 와 근접** — import 경로(`maple_mate.scheduler` vs `maple_mate.notification.scheduler`)로 구별되나 소폭 혼동 여지(도메인명 일치를 우선).
- **단일 인스턴스 전제** — 디스패치 cron·구독 조회는 단일 프로세스 가정(쿨다운·스로틀과 동일, 분산 시 재검토).
