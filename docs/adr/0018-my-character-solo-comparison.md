# ADR-0018 — `/내캐릭터` 솔로 비교: 별도 명령 그룹 + exp_snapshot PK ocid 확장 + realm 혼합

- **상태:** 채택 (Accepted)
- **일자:** 2026-07-02
- **관련 문서:** [my-character-work-order.md](../my-character-work-order.md)(빌드 단위·검증 게이트), [CONTEXT.md](../../CONTEXT.md)("캐릭터 타깃" 용어), [ADR-0006](0006-multi-character-data-model.md)→[ADR-0009](0009-challengers-realm-model.md)(exp_snapshot PK 확장 전례 — **본 ADR이 PK 서술을 재개정**), [ADR-0011](0011-exp-leaderboard-display.md)(Top10·절대레벨 표시 — 재사용), [ADR-0015](0015-history-account-identity-display.md)(이력류 계정 정체성 — 스코프아웃 근거)
- **이력:** `/grill-me` 그릴링(2026-07-02) — 결정 9건 확정. PR1(스펙·아이템, 스키마 무변경) / PR2(경험치, 마이그레이션 1건) 분할.

## 맥락 (Context)

비교류 명령(`/스펙`·`/아이템`·`/경험치`)은 전부 **유저 간 비교**다 — 유저당 대표 캐릭터 1명을 Target으로 해석해 서버 등록자끼리 견준다. 같은 디스코드 서버에 비교할 친구가 없는 **솔로 유저는 쓸 명령이 없다**. 한편 멀티 캐릭터 모델(유저당 상한 10, ADR-0006)로 본인 캐릭터가 이미 여러 개 등록돼 있으므로, **본인 캐릭터끼리 비교**가 자연스러운 해법이다.

제약 세 가지:
1. 디스코드 슬래시 커맨드는 **조건부 필수 파라미터를 표현하지 못한다** — `/스펙`의 member1(필수)에 "내캐릭터" 옵션을 얹으려면 member1을 optional로 풀어야 하고, 이는 기존 동작 변경(무인자 `/스펙`이라는 새 상태)이자 팬아웃 경계(이슈0001)와 충돌한다.
2. `/경험치`의 소스 `exp_snapshot`은 PK `(guild_id, discord_user_id, snapshot_date, realm)`로 **캐릭터 차원이 없다** — 캐릭별 추이는 스키마 확장 없이 불가능.
3. realm 불변식("본서버 비교에 챌린저스 불혼입", ADR-0009)은 **유저 간 공정성**을 위한 것 — 본인 캐릭끼리는 그 전제가 성립하지 않는다.

## 결정 (Decision)

**통합 명령 그룹 `/내캐릭터`(서브커맨드 `스펙`·`아이템`·`경험치`)를 신설하고, 기존 유저 간 비교 명령은 한 줄도 바꾸지 않는다(회귀 0).**

1. **모드 진입 = 별도 명령 그룹** (`app_commands.Group(name="내캐릭터")`). 기존 명령 파라미터 확장은 기각 — member1 조건부 필수 불가(제약 1). 렌더 경로는 이미 `Target.nickname` 기준이라 **캐릭터당 Target 1개**(캐릭터 타깃)를 주입하면 fetch·표·카드가 무수정으로 동작한다.

2. **스코프 = 스펙·아이템·경험치 3종.** 유니온은 계정 단위 수치라 캐릭터 비교가 무의미 → 제외. 이력류(스타포스·잠재)는 계정 합산 정체성(ADR-0015)과 충돌 → 스코프아웃.

3. **캐릭터 선택**: 무인자 = 등록 캐릭터 전체. 스펙·아이템은 렌더 폭+팬아웃 비용 때문에 **등록 레벨(DB) 상위 5 절단 + 안내 푸터**, `캐릭터1~5` 자동완성 파라미터로 명시 지정 가능(입력 순서 보존). 경험치는 저비용(DB 조회)이라 무인자 = 전체 최대 10(Top10 파이프라인과 정합).

4. **realm 혼합, 모드 파라미터 없음.** 본인 캐릭끼리라 realm 공정성 전제가 없다(제약 3) — 챌린저스 캐릭터는 **라벨에 월드명 병기**(`닉 (챌린저스N)`)로만 구분한다. ADR-0009의 "본서버 비교에 챌린저스 불혼입" 불변식은 **유저 간 비교 한정**으로 정밀화한다.

5. **경험치 수집 = 스케줄러 전 캐릭터 확장 (PR2).** 매일 수집 대상을 대표 → 등록 전 캐릭터로 넓힌다. 온디맨드 백필 단독안은 기각(응답 즉시성 우선, 일일 콜 ≤10배 증가는 전역 4req/s 스로틀 내 순차 처리로 감수 — 수집 윈도우만 늘어남).

6. **스키마 = exp_snapshot 단일 테이블 PK에 ocid 추가 (PR2).** 목표 PK `(guild_id, discord_user_id, ocid, snapshot_date)` — `ocid` PK 승격, **`realm`은 PK에서 강등해 일반 컬럼 존치**(ocid가 행 유일성을 더 정밀하게 보장, realm은 서버 리더보드 필터용 디스크리미넌트). 기존 행은 "그 realm의 현재 대표 ocid"로 백필하고, 대표를 해석할 수 없는 고아 행은 삭제. 서버 리더보드는 대표 ocid 행만 조회해 **표시 결과 불변**. 새 테이블 분리안은 기각(대표 캐릭터 이중 수집 = 같은 사실의 소스 2개).

7. **출력 = 채널 공개**(기존 비교류와 동일). 0캐릭 에러·DM 거부만 ephemeral. 1캐릭은 graceful(스펙=단일 상세 임베드, 아이템=카드 1장, 경험치=1라인 그래프 — 에러 아님).

8. **분할 = 2 PR.** PR1 = `/내캐릭터 스펙`·`아이템`(스키마 무변경) + 사이트 문서. PR2 = `경험치`(마이그레이션 + 스케줄러 확장).

## 검토한 대안 (Alternatives Considered)

- **기존 명령에 "내캐릭터" 파라미터 추가** — *기각.* member1 조건부 필수를 슬래시가 표현 못 해 기존 필수성을 풀어야 하고(동작 변경), 무인자 `/스펙`이라는 새 팬아웃 상태가 생긴다(결정 1).
- **명령 3개 개별 신설(`/내스펙` 등)** — *기각.* 트리 오염 + 발견성 저하. 그룹 1개가 `/경험치알림 켜기·끄기` 전례와 정합(결정 1).
- **경험치 온디맨드 백필 단독(스케줄러 무확장)** — *기각.* 콜드 실행마다 캐릭당 ≤8콜 팬아웃으로 응답이 느리고, 스로틀 경쟁을 명령 시점으로 옮길 뿐이다(결정 5).
- **캐릭별 스냅샷 새 테이블 분리** — *기각.* 대표 캐릭터가 두 테이블에 이중 수집돼 같은 사실의 소스가 2개가 된다(결정 6).
- **`/내캐릭터`에도 모드 파라미터 부착** — *기각.* 본인 캐릭끼리는 realm 공정성 전제가 없고, 특정 realm만 보고 싶으면 캐릭터 지정으로 해결된다(결정 4).

## 결과 (Consequences)

- 솔로 유저도 등록 즉시 비교류 가치를 얻는다 — 캐릭터 등록(tier: character)만으로 스펙·아이템, PR2 이후 경험치까지.
- (PR2) 마이그레이션 백필이 "현재 대표" ocid를 과거 행에 소급하므로, 과거에 다른 대표였던 기간의 행이 현재 대표 이름표를 달게 된다 — 데이터가 유저 단위였던 이상 불가피한 근사. 이후로는 캐릭터별로 정확히 쌓인다(부수효과: 대표 교체에도 이력 보존).
- (PR2) 일일 수집이 등록 캐릭터 수에 비례해 늘어난다(≤10배). 전역 스로틀이 보호하므로 기능 위험은 없고 10:00 수집 윈도우만 길어진다 — 캐릭터 수 급증 시 팬아웃 경계 작업(이슈0001)에서 재론.
- PR1↔PR2 사이엔 `/내캐릭터`에 경험치 서브커맨드가 없는 기간이 존재 — 드리프트 가드(웹사이트↔봇트리)가 각 PR 시점의 정확한 문서화를 강제한다.
