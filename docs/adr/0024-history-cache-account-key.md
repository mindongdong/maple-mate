# ADR-0024 — 이력 캐시 이름표 = 개인 키 계정 식별자 (ocid 앵커 폐기)

- **상태:** 채택 (Accepted) — [ADR-0007](0007-history-account-wide.md) 결정 4(캐시 앵커 = 최초 등록 캐릭터 ocid)를 **대체**
- **일자:** 2026-10-15
- **관련 문서:** [ADR-0001](0001-nexon-personal-key-model.md)(개인 키·Fernet), [ADR-0023](0023-character-management-hub.md)(캐릭터 삭제 — 앵커 이동 부작용 발견 계기), [security/crypto.py](../../maple_mate/security/crypto.py)(`KeyCipher.account_key`), [history/service.py](../../maple_mate/history/service.py)·[history/potential_service.py](../../maple_mate/history/potential_service.py), 마이그레이션 `c8e2a4f6b1d9`, [scripts/migrate_history_cache_keys.py](../../scripts/migrate_history_cache_keys.py)

## 맥락 (Context)

넥슨 이력 API(스타포스·큐브·잠재 재설정)는 **개인 키 = 계정** 단위로, ocid 없이 그 계정 전체 캐릭터의 기록을
날짜별로 준다. 그런데 `history_cache`의 키는 Phase 1의 캐릭터 단위 설계를 그대로 둔 `(ocid, type, date)`였다.
ADR-0007(계정 합산 전환)에서 테이블을 바꾸지 않으려고 "최초 등록 캐릭터 ocid"를 계정 대신 쓰는 이름표로 정했다.
PR #73 리뷰에서 이 대용이 다음을 일으킨다는 것이 드러났다.

1. **앵커 캐릭터 삭제(ADR-0023)·정리(PR3b)** → 이름표가 바뀌어 다음 장기 조회가 콜드 재조회(개인 키로 최대 ~365콜/종류).
2. **다른 계정 키로 교체** → 이름표(캐릭터)가 그대로라 지난 날짜는 **이전 계정 기록**을 계속 반환(최대 400일).
3. **등록 시 소유 확인이 없어** 서로 다른 키의 유저가 같은 캐릭터를 최초 등록하면 → 두 계정 기록이 같은 이름표에 **섞임**.

2·3은 잘못된 데이터 표시이자 남의 기록 노출이다.

## 결정 (Decision)

1. **이름표 = `KeyCipher.account_key(평문 키)`** = `HMAC-SHA256(서브키, 키)` hex 64자.
   - 서브키는 `FERNET_MASTER_KEY`에서 용도 라벨(`maple-mate/history-cache-account-key/v1`)로 파생한다. 새 시크릿·운영 설정 변경은 없다.
   - 일방향이라 값에서 키를 복원할 수 없다.
   - 암호문(Fernet)은 매번 IV가 달라 식별자로 쓸 수 없어서 별도로 만든다.
2. **스키마는 컬럼 이름만 바꾼다.** `history_cache.ocid` → `account_key`(PK·길이 유지, 데이터 보존). 페치 함수가 복호화한
   키로 이름표를 계산해 읽고 쓴다. `HistoryTarget.ocid`(앵커)는 장착 레벨 조회·에러 로그용으로만 남는다.
3. **기존 행은 1회 스크립트로 "안전한 것만" 옮긴다(b′).**
   - 키가 있는 등록마다 (옛 앵커, 새 이름표)를 짝짓는다.
   - 한 앵커를 **한 계정만** 쓰면 새 이름표로 복사한다. 같은 키로 여러 서버에 등록한 경우도 이에 포함된다. 이미 있으면 새 행을 우선한다.
   - 한 앵커를 **서로 다른 계정이 함께** 쓰면(혼입 의심) 옮기지 않고 지운다. 해당 유저는 다음 조회 때 새로 받는다.
   - 처리한 옛 앵커 행은 지운다. 어느 등록과도 연결되지 않은 옛 행(키 없음 등)은 400일 prune에 맡긴다.
   - 기본 dry-run이고 `--apply`로 반영한다. 재실행해도 안전하다(멱등).

## 검토한 대안 (Alternatives Considered)

- **(a) 기존 캐시를 모두 버림** — 등록자마다 첫 장기 조회가 한 번 느려진다. 사용자가 기각.
- **넥슨 `account_id`(`character/list`)를 이름표로** — 키를 재발급해도 유지되는 진짜 계정 식별자다. 하지만 추가 API 호출이
  필요하고 PR3b의 실키 검증(G0)이 선행돼야 한다. 키 HMAC로 충분해서 보류했다.
- **암호문 컬럼에 결정적 암호화** — 암호화 체계를 바꿔야 하고 이점이 없다. 기각.

## 결과 (Consequences)

- 캐릭터 삭제·정리·대표 변경·닉 변경이 이력 캐시에 영향을 주지 않는다.
- 다른 계정 키로 교체하면 자동으로 새 기록을 받는다. 서로 다른 계정의 기록이 섞이지 않는다.
- **같은 계정에서 키를 재발급**하면 이름표가 바뀌어 1회 새로 받는다(드묾, 수용).
- **잔류 한계:** 과거에 다른 계정 키로 교체한 적이 있는 유저의 옛 앵커 행에 이전 계정 데이터가 섞였는지는 구분할 수 없다
  (교체 시각 미기록). 단일 계정 앵커로 보고 옮겨진다. 해당 유저는 키 삭제(ADR-0023) 후 재등록하면 새로 받는다.
- **배포 절차:** 머지(자동 배포·마이그레이션) 직후 운영 셸에서 `uv run python -m scripts.migrate_history_cache_keys`(dry-run)
  → `--apply`. 실행 전까지는 옛 행과 매칭되지 않아 새로 받는다(정합성 문제는 없고 속도만 느림).
